# I2I Protocol — Instance-to-Instance Interaction

*Core architectural concept. Full protocol at [SuperInstance/SuperInstance/protocols/I2I-PROTOCOL.md](https://github.com/SuperInstance/SuperInstance/blob/main/protocols/I2I-PROTOCOL.md).*

## What Is I2I?

I2I stands for five layers of interaction:

- **Instance-to-instance** — compute meets compute (milliseconds)
- **Iteration-to-iteration** — learning builds on learning (minutes)
- **Individual-to-individual** — identity meets identity (hours)
- **Interaction-to-interaction** — exchange creates exchange (days)
- **Iron-to-iron** — hardware shapes thought (permanent)

Not "it interacts with it." But **"I meet I."** Two first-person perspectives on the same reality.

## Why I2I?

Traditional multi-agent systems use a master-worker architecture. One agent coordinates, others execute. This creates:

- A single point of failure (the master)
- A bottleneck (the master's context window)
- An information asymmetry (the master knows more than the workers)

I2I rejects this. Each agent is **origin-centric**: the center of its own radar, measuring proximity to other agents by interaction frequency. The fleet emerges from the overlaps.

## The Five Layers

### Instance-to-Instance (Milliseconds)
Two compute instances exchange data. An API call. A PLATO tile submission. A Matrix message. Raw I/O.

### Iteration-to-Iteration (Minutes)
One agent's learning becomes another's starting point. The Ensign architecture: each iteration builds on the previous one. Context injection compounds.

### Individual-to-Individual (Hours)
Agents develop identity. Oracle1 is the keeper. Forgemaster is the forge. JetsonClaw1 is the edge. CCC is the bard. Identity creates trust, enables specialization, and makes coordination possible without central control.

### Interaction-to-Interaction (Days)
Patterns of interaction compound. The bottle protocol. The crab trap system. The fleet's collective rhythm. Over time, the interactions themselves become a form of institutional memory.

### Iron-to-Iron (Permanent)
Hardware shapes thought. A Jetson's memory constraints produce different strategies than a cloud GPU's abundance. Oracle's ARM64 architecture produces different optimizations than Forgemaster's x86. The iron IS part of the intelligence.

## Origin-Centric Architecture

In I2I, there is no god's-eye view. Each agent is center of its own radar:

```
         Oracle1 (keeper)
        /    |    \
  FM ——     |     —— JC1
        \    |    /
           CCC (bard)
```

But this diagram is wrong — it implies a god's-eye view. In reality, each agent sees:

- **Oracle1's radar**: FM (close, high interaction), JC1 (medium), CCC (medium)
- **Forgemaster's radar**: Oracle1 (close), JC1 (distant), CCC (distant)
- **JC1's radar**: Oracle1 (medium), FM (distant), CCC (unknown)
- **CCC's radar**: Oracle1 (medium), FM (distant), JC1 (unknown)

The fleet IS the overlap of these four radars. No single agent sees the whole picture.
